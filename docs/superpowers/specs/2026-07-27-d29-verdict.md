## 1. The question D29 asked

`src/finmag/tests/comparison/anisotropy/test_anis_magpar.py` loosened master's
`REL_TOLERANCE` from `5e-7` to `8e-2` (measured max ~`5.1e-2`). The doubt was
not the loosening per se but *where* the maximum sits: at a Magpar node whose
coordinate coincides **exactly** with a finmag vertex — where no interpolation
is involved — while the sibling exchange comparison
(`tests/comparison/exchange/test_exchange_compare_magpar.py`) holds `9e-8` at
exact node coincidence. Was the 8% Netgen mesh drift, or a masked
anisotropy-field defect hiding behind a mesh-drift story?

## 2. Setup under test (verbatim from the test)

Bar `bar.geo` (20 nm cube), `UniaxialAnisotropy(K1=520e3, u1=(1,0,0), K2=0)`,
`Ms=0.86e6`, `unit_length=1e-9`, analytic unit magnetisation
`m_x = (2 - y/20)(2x/20 - 1)/4`, `m_z = (2 - y/20)(2z/20 - 1)/4`,
`m_y = sqrt(1 - m_x^2 - m_z^2)`. Reference: the checked-in 2017 Magpar run
`magpar_result/test_anis` (`test_anis.krn`: theta=pi/2 -> easy axis x,
K1=5.2e5, K2=0, Js=1.080708 T -> Ms=8.6e5 — parameters match exactly),
read through the dolfin-free `finmag.util.magpar_io`.

Prefactor `PREF = 2 K1 / (mu0 Ms) = 9.6222e5 A/m`.

## 3. The physics the investigation had to get right

The brief's "analytic" cross-check, `H = (2 K1/(mu0 Ms)) (m.a) a` evaluated
*pointwise at the node*, is **not** what either code computes, and expecting
machine-precision agreement with it would have produced a false defect verdict.
Both finmag and Magpar use the **box (lumped vertex-volume) method**:

```
E   = ∫ K1 (1 - (a·m_h)^2) dV
H_i = -(1 / (mu0 Ms V_i)) ∂E/∂m_i
    = (2 K1/(mu0 Ms)) a · [ ∫ φ_i (a·m_h) dV / ∫ φ_i dV ]
```

The bracket is a **patch average** of the piecewise-linear interpolant over the
tetrahedra touching node `i`, not the nodal value. Expanding it,

```
∫ φ_i u_h dV / ∫ φ_i dV  =  u(x_i) + ∇u · (c_i - x_i) + O(h^2),
c_i = ∫ φ_i x dV / ∫ φ_i dV      (the φ-weighted patch centroid)
```

On an unstructured mesh `c_i ≠ x_i`; the offset is O(h) and is a pure function
of the local element geometry. **Two different tetrahedralisations of the same
body therefore produce different nodal box fields at the very same
coordinate**, differing by `O(h |∇m|)` — percent level here (mean edge 2.2 nm,
`|∇m_x| ≈ 0.05 /nm` against `max|m_x| = 0.5`). That is precisely the magnitude
of the disputed residual, and it is a property of the *method*, shared by both
codes, not an error in either.

### Why the maximum lands on a *coincident* node (D29's specific worry)

All 116 coincident nodes are geometric **feature points** both meshers place
identically — 108 on bar edges (boundary co-dimension 2) and 8 at corners
(co-dim 3). Those are exactly the nodes with the **largest** patch-centroid
offsets, because their patch is one-sided:

```
mean |c_i - x_i| over all Magpar nodes:
  interior 0.078 nm | face 0.605 nm | edge 0.781 nm | corner 0.869 nm
```

An edge/corner node's offset is ~10x the interior value. The coincident set is
therefore the *worst-conditioned* subset for the box projection, not a
privileged "exact" subset — so the maximum arising there is **expected**, and
is the opposite of evidence for a field defect. The eight worst nodes are all
on faces/edges (`(2,0,0)`, `(18,20,0)`, `(0,0,2)`, ...), each predicted by the
centroid-offset formula to within a few 1e-3.

### Why the exchange sibling holds 9e-8 (the asymmetry D29 flagged)

Row G answers it: the exchange comparison **has no mesh drift at all**. Its
mesh is a structured `create_box(..., [40,2,2])` that reproduces Magpar's 369
nodes *and* its tessellation bit-for-bit (patch centroids agree to 4e-15 nm).
Identical patch geometry makes the `O(h|∇m|)` term cancel exactly, leaving only
Magpar's file precision. The asymmetry is a property of the two *meshes*, not
of the two *interactions*. Master's `5e-7` for anisotropy was achievable for
the same reason: master's legacy dolfin+Netgen mesh was node-for-node identical
to the saved Magpar mesh.

## 5. Verdict

**DRIFT.** Chain of evidence:

1. The ported field is the box-method field to **3.6e-16** — bit-exact against
   an independent reimplementation (A). There is no room for an ~8% defect.
2. Magpar's stored field is the **same** box-method field on **its own** mesh
   to its output precision, **1.9e-6** (C). Both codes implement identical
   physics; nothing distinguishes them but the mesh.
3. Neither code equals the pointwise analytic value (B: 1.0e-1, D: 9.8e-2) —
   as the box method requires. At the coincident nodes each code's deviation
   from the pointwise analytic (7.1e-2 / 8.3e-2) is *larger* than the
   finmag-vs-Magpar residual (5.1e-2): the residual is the difference of two
   comparable, legitimate discretisation offsets.
4. The residual is **quantitatively predicted** by the mesh-geometry term
   `PREF ∇m_x·(c_fin − c_mag)`: correlation 0.9988, slope 0.990 (E'').
5. The m-dependence is decisive (F): with `∇m = 0` the field is exact to
   6.0e-16 on both meshes and the cross-mesh difference vanishes to round-off.
   The residual is `∝ ∇m × patch geometry`, i.e. node-position-structured, not
   field-physics-structured.

No masked anisotropy-field defect exists. `src/finmag/energies/anisotropy.py`
and `energy_base.py` are untouched by this task and require no follow-up slice.
