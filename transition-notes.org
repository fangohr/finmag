* Finmag Transition Notes

** Purpose

This file records concrete environment and packaging findings relevant to the
transition from:

- Python 2 to Python 3
- old `dolfin` packaging to a reproducible Python 3 runtime for the same
  DOLFIN generation

The emphasis here is on exact versions, package sources, and constraints that
were observed directly during probing.

** Current Reference Environment

Reference container:

- `finmag/finmag:latest`

Verified contents:

- `python` = Python 2.7.12
- `python3` = Python 3.5.x
- `python` can import `dolfin`
- `python3` cannot import `dolfin`

- `dolfin.__version__ == 2017.1.0`

Installed package metadata observed in the container:

- binary packages come from `ppa:fenics-packages/fenics`
- the `deb-src` entry for that PPA was commented out by default

** Important Constraint

Ubuntu/xenial packaging in the current Finmag image provides:

- `python-dolfin`

but not:

- `python3-dolfin`

for the installed `2017.1.0` stack.

This is why the Python 3 port can proceed with syntax and import cleanup, but
cannot yet run Finmag end to end under Python 3 in the current image.

** Upstream / Packaging Findings

*** DOLFIN 2017.1.0

During probing we established that upstream `dolfin 2017.1.0` switched the
default build to Python 3, with Python 2 requiring:

- `-DDOLFIN_USE_PYTHON3=off`

This is important because it means a Python 3 build of the 2017 generation is
not conceptually alien to DOLFIN itself; the limitation is mainly packaging and
dependency availability in the current reference image.

*** PPA Source Mismatch

After enabling the PPA `deb-src` entry in a disposable container, `apt-get
source dolfin` did not fetch `2017.1.0`. It fetched:

- `dolfin 2019.1.0-1~ppa0~xenial2`

This means the current PPA source state no longer matches the installed binary
`2017.1.0` packages in `finmag/finmag:latest`.

So:

- the PPA is useful to inspect newer packaging patterns,
- but not sufficient to reconstruct the exact old source package used by the
  reference image.

** Snapshot Package Resolution Notes

Initial install probing against the `20170920T000000Z sid` snapshot showed:

- installing `python3-dolfin=2017.1.0-4` alone is insufficient
- it requires `libdolfin-dev=2017.1.0-4`
- `libdolfin-dev=2017.1.0-4` in turn requires additional dev/runtime packages,
  including:
  - `libhdf5-mpi-dev`
  - `libscotch-dev`
  - `libvtk6-dev`
  - `libpetsc3.7.6-dev`
  - `libslepc3.7.4-dev`

This means the snapshot image needs either:

1. a broader install of the full matching dependency closure from the same
   snapshot, or
2. a staged `dist-upgrade` onto that historical snapshot before package
   installation.

The experimental Dockerfile under:

- `install/docker/python3-dolfin2017-snapshot/Dockerfile`

follows the second approach.

- Ubuntu 18.04 (`bionic`) offers `dolfin 2017.2.0.post0-2`, not `2017.1.0`

- Debian snapshot `20170920T000000Z sid`

** Working Assumption Going Forward

For the purpose of getting Finmag running under Python 3 with an old DOLFIN
stack, the most promising path is:

1. build or install a Python 3 environment from the Debian snapshot carrying
   `python3-dolfin=2017.1.0-4`,
2. copy the Finmag checkout into that environment,
3. continue validating:
   - `python3 -c "import dolfin"`
   - `python3 -c "import finmag"`
   - then progressively larger test subsets.

** Open MPI Runtime Note

Importing `dolfin` in this snapshot-based image triggers MPI initialization.
In both Docker build and container runtime contexts, this required:

- `OMPI_MCA_plm=isolated`

Without that override, `import dolfin` failed with Open MPI errors about:

- `plm_rsh_agent`
- `Unable to start a daemon on the local node`
- `MPI_Init_thread`

So the current working assumption is that any Python 3 Finmag test runs in this
image should start with at least:

- `OMPI_MCA_plm=isolated`

** What Fixed The Runtime Regression

After `import finmag` was working, the next blocker was a CVODE runtime failure
even for trivial ODEs under Python 3:

- `CV_CONV_FAILURE` at `t = 0`

Important narrowing observations:

- the same `barmini().run_until(1e-12)` step succeeds in the Python 2 reference image
- the initial Finmag RHS for `barmini` is identical in Python 2 and Python 3
- even a one-dimensional test problem `y' = 0.5 y` failed in the Python 3 image

This showed that the regression was in the native Sundials/NVector runtime
path, not in the Python-level field setup.

The fix that restored runtime integration was:

- stop linking the Python 3 Sundials module against Finmag's vendored custom
  `libnvector_serial_custom_malloc`
- link it against the system:
  - `libsundials_nvecserial`
- construct callback-local NumPy array views directly from raw NVector memory in:
  - `native/src/sundials/numpy_malloc.cc`

This keeps the callback bridge working under Python 3 while avoiding the
runtime incompatibility between the old vendored NVector implementation and
SUNDIALS `2.7.0`.
