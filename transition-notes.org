* Finmag Transition Notes

** Purpose

This file records concrete environment and packaging findings relevant to the
transition from:

- Python 2 to Python 3
- old `dolfin` packaging to a reproducible Python 3 runtime for the same
  DOLFIN generation

The emphasis here is on exact versions, package sources, and constraints that
were observed directly during probing.

** Strategic Direction

The transition is now treated as four separate milestones, not one continuous
upgrade:

1. Python 3 usability on the current legacy =dolfin 2017.1.0= transition
   stack;
2. a user-facing installation path outside the specialist container workflow,
   preferably via =pixi=;
3. migration to legacy FEniCS/=dolfin 2019.1.0=;
4. a later, reduced-scope =dolfinx= port.

This matters because legacy FEniCS and =dolfinx= are different targets with
different risks. The last legacy FEniCS release is =2019.1.0=; =dolfinx= is a
separate actively developed stack and should be handled as a redesign/porting
track rather than a routine package upgrade.

Guiding rule:

- do not spend time reviving old features unless that work directly helps one
  of the four milestones above.

In practice this means:

- keeping historical xfails and niche comparison paths deferred when they do
  not block Python 3, =pixi=, =dolfin 2019.1.0=, or =dolfinx=;
- preferring a small stable workflow matrix over broad historical parity;
- using the current Python 3 core gate as the main M1 regression baseline.

*** Likely external or project-specific work, even with `pixi`

The following items look like they will still need custom handling:

- Finmag packaging itself
  - there is no modern top-level package metadata yet
  - M2 needs a real install layout, not just dependency installation
- `dolfinh5tools`
  - this is an external companion package, not part of Finmag
  - the current Python 3 image installs it directly from GitHub and patches it
  - for `pixi`, this likely needs either:
    - a pip dependency from GitHub, or
    - a separate package recipe / packaging story
- Finmag native extensions
  - `native/Makefile` still drives the build
  - M2 needs a decision on whether `pixi` invokes that build explicitly or
    whether packaging is taught to build/install these extensions
- OOMMF integration details
  - package availability now looks good, but Finmag depends on the
    Southampton/Fangohr fork and on executable discovery conventions
  - M2 should verify that the conda-forge `oommf` package is functionally
    equivalent for Finmag's comparison helpers
- Netgen runtime behavior
  - package availability is not the same as runtime reliability
  - the current Python 3 transition image still needs compatibility handling
    for the historical `netgen 4.9.13` shutdown bug and Tcl/Tix paths
  - a `pixi` environment will need its own probe and validation path

*** Likely blockers for a full M2 environment on the current 2017 stack

These look like the main risks for a full `pixi` environment that reproduces
the current M1 stack exactly:

- exact legacy `dolfin 2017.1.0`
  - the current working environment depends on a Debian snapshot package set
  - the conda-forge route is much more naturally aligned with legacy
    `fenics 2019.1.0` than with this exact `2017.1.0` stack
- direct parity with the current container's native-library mix
  - the container uses historical Debian package versions and local native
    compatibility fixes
  - `pixi` may be an easier fit once the project moves to M3
- historical optional tool paths
  - `nsim`
  - Mercurial / `hg`
  - GUI-heavy Paraview workflows
  - these should not block M2 unless we decide they are part of the supported
    user-facing environment

*** Current recommendation for M2

Do not aim first for:

- "reproduce the whole M1 Debian-snapshot stack in pixi"

Aim first for:

- a `pixi`-managed environment for the Python-facing Finmag package and its
  practical workflows,
- most likely using conda-forge `fenics 2019.1.0` as the more natural legacy
  FEniCS packaging target,
- while treating exact `2017.1.0` parity as a container-only reference.

That suggests the packaging track and the M3 legacy-FEniCS-2019 track may be
partly coupled in practice.

*** Proposed first `pixi` target

The first `pixi` attempt should be intentionally narrow.

Recommended target environment contents:

- `python`
- `pip`
- `setuptools`
- `cython`
- `numpy`
- `scipy`
- `matplotlib`
- `pytest`
- `fenics = 2019.1.0`
- `petsc4py`
- `slepc4py`
- `gmsh`
- `netgen`

Recommended initial omissions:

- `oommf`
- `paraview`
- GUI/rendering support
- `nsim`
- Mercurial / `hg`
- any attempt to preserve exact `dolfin 2017.1.0` package parity

Recommended first acceptance checks for M2:

1. `pixi run import-finmag`
2. `pixi run barmini-construct`
3. `pixi run barmini-smoke`

Recommended interpretation of the outcomes:

- if step 1 fails, the blocker is packaging/import-level and M2 should stay
  focused there;
- if steps 1 and 2 pass but step 3 fails, M2 has still made real progress,
  but the native-build/runtime path needs a second pass;
- if all three pass, M2 has a credible first user-facing environment even
  before optional tools are layered in.

*** Suggested next M2 deliverables

In order:

1. add a first `pixi.toml` to the repo, even if incomplete;
2. add a minimal packaging/install story for Finmag itself;
3. document the exact `pixi` commands for environment creation and the first
   acceptance checks above;
4. only then broaden to optional tools such as OOMMF or visualization.

** Upstream / Packaging Findings

*** DOLFIN 2017.1.0

During probing we established that upstream `dolfin 2017.1.0` switched the
default build to Python 3, with Python 2 requiring:

- `-DDOLFIN_USE_PYTHON3=off`

This is important because it means a Python 3 build of the 2017 generation is
not conceptually alien to DOLFIN itself; the limitation is mainly packaging and
dependency availability in the current reference image.

*** PPA Source Mismatch

After enabling the PPA `deb-src` entry in a disposable container, `apt-get
source dolfin` did not fetch `2017.1.0`. It fetched:

- `dolfin 2019.1.0-1~ppa0~xenial2`

This means the current PPA source state no longer matches the installed binary
`2017.1.0` packages in `finmag/finmag:latest`.

So:

- the PPA is useful to inspect newer packaging patterns,
- but not sufficient to reconstruct the exact old source package used by the
  reference image.

** Snapshot Package Resolution Notes

Initial install probing against the `20170920T000000Z sid` snapshot showed:

- installing `python3-dolfin=2017.1.0-4` alone is insufficient
- it requires `libdolfin-dev=2017.1.0-4`
- `libdolfin-dev=2017.1.0-4` in turn requires additional dev/runtime packages,
  including:
  - `libhdf5-mpi-dev`
  - `libscotch-dev`
  - `libvtk6-dev`
  - `libpetsc3.7.6-dev`
  - `libslepc3.7.4-dev`

This means the snapshot image needs either:

1. a broader install of the full matching dependency closure from the same
   snapshot, or
2. a staged `dist-upgrade` onto that historical snapshot before package
   installation.

The experimental Dockerfile under:

- `install/docker/python3-dolfin2017-snapshot/Dockerfile`

follows the second approach.

** What Fixed The Runtime Regression

After `import finmag` was working, the next blocker was a CVODE runtime failure
even for trivial ODEs under Python 3:

- `CV_CONV_FAILURE` at `t = 0`

Important narrowing observations:

- the same `barmini().run_until(1e-12)` step succeeds in the Python 2 reference image
- the initial Finmag RHS for `barmini` is identical in Python 2 and Python 3
- even a one-dimensional test problem `y' = 0.5 y` failed in the Python 3 image

This showed that the regression was in the native Sundials/NVector runtime
path, not in the Python-level field setup.

The fix that restored runtime integration was:

- stop linking the Python 3 Sundials module against Finmag's vendored custom
  `libnvector_serial_custom_malloc`
- link it against the system:
  - `libsundials_nvecserial`
- construct callback-local NumPy array views directly from raw NVector memory in:
  - `native/src/sundials/numpy_malloc.cc`

This keeps the callback bridge working under Python 3 while avoiding the
runtime incompatibility between the old vendored NVector implementation and
SUNDIALS `2.7.0`.

** First M5 / DOLFINx Core Simulation Slice

M5 starts with a reduced core-path wrapper rather than a legacy API port:

- =dev/dolfinx/simulation.py= introduces =PrototypeSimulation=, composing the
  checked M4 DOLFINx helpers for mesh creation, magnetisation setup,
  exchange/Zeeman/anisotropy energy reporting, average magnetisation, one-step
  explicit LLG updates, and short relaxation histories
- =dev/dolfinx/test_simulation.py= covers supported energy terms, relaxation
  energy decrease, custom parameters, and invalid wrapper controls
- the wrapper exposes a JSON-compatible state summary that reports mesh label,
  average magnetisation, parameters, and energy terms without advancing the
  simulation
- the reduced wrapper exposes a JSON-compatible relaxation summary as a basic
  output path for the first M5 core sketch
- the wrapper summary is checked with the existing relaxation summary validator
  and includes =dolfinx_version= plus schema version
- the wrapper can write the validated relaxation summary to JSON, matching the
  practical output path used by the M4 example
- the wrapper can emit a JSON-compatible per-step relaxation trace with time,
  average magnetisation, and energy terms; this is a small data-I/O contract,
  not legacy NDT, VTK/XDMF, or scheduler support
- the wrapper can write and read a narrow JSON restart state for the
  =PrototypeSimulation= unit-square path; this captures nodal magnetisation
  values and parameters, not a general Finmag restart format
- =dev/dolfinx/restart_example.py= is a runnable restart-state round-trip
  witness, and the DOLFINx verification wrapper now runs it through the
  =dolfinx-restart-example= pixi task

This is intentionally not =finmag.Simulation= compatibility. It is a small API
sketch to make the next DOLFINx core path reviewable. [Codex gpt-5.5 high]
